# TLS lab

Цель: посмотреть серт, понять ошибку curl, выпустить серт, подложить его nginx и не забыть reload.
Этого хватит для стажёра и для Geneva.

Готовых команд тут нет специально. Ищи их в шпаргалке `TLS.md`.
После каждого задания пиши «проверь N».

---

## Часть 1. Свой серт + nginx

```bash
mkdir certs nginx
```

**1.** Выпусти self-signed серт для `localhost` на 30 дней. Ключ клади в `certs/key.pem`, серт в `certs/cert.pem`, в SAN должен быть `localhost`.
Потом выведи из серта только три вещи: кому выдан, кем выдан и до какого числа действует.
Почему «кому» и «кем» совпадают?

<details><summary>подсказка</summary>

Ключ должен быть без пароля, иначе nginx при старте попросит его ввести.
</details>

**2.** Подними nginx, который по https отвечает `hello tls`. Конфиг `nginx/default.conf` пишешь сам.

```bash
docker run -d --name tls -p 8443:443 -v ./nginx:/etc/nginx/conf.d -v ./certs:/certs nginx:1.30-alpine
```

<details><summary>подсказка</summary>

Обычный `server { }` и в нём три строки: одна велит слушать порт по TLS, две говорят, где серт и где ключ.
Пути пиши такие, какими их видит контейнер, а не хост. Директивы ищи в доке nginx, модуль `ngx_http_ssl_module`.
Если контейнер упал, смотри его логи.
</details>

**3.** Сходи curl'ом на `https://localhost:8443` тремя способами:
- просто, без флагов
- так, чтобы curl вообще не проверял серт
- так, чтобы curl доверял именно твоему серту

Для каждого способа одной фразой: что получилось и почему.
Почему второй способ нельзя оставлять в проде и в скриптах?

**4.** Сходи третьим способом на `https://127.0.0.1:8443`. Почему падает?
Перевыпусти серт так, чтобы работали и `localhost`, и `127.0.0.1`.
Подложи его nginx, **не пересоздавая контейнер**, и проверь оба адреса.

<details><summary>подсказка</summary>

Прочитай ошибку целиком: в ней прямо сказано, чего не хватает. SAN бывает не только `DNS:`.
</details>

<details><summary>подсказка 2</summary>

Файл заменил, а curl всё ещё видит старый серт? Значит, nginx его не перечитал.
</details>

**5.** Посмотри срок серта двумя путями:
- у файла `certs/cert.pem`
- у серта, который **реально отдаёт** nginx на 8443

В какой ситуации эти два срока будут разными?
Потом одной командой проверь, истечёт ли серт в ближайшие 60 дней. Ответ смотри по коду выхода (`echo $status` в fish).

<details><summary>подсказка</summary>

Второй путь ты уже делал с github.com. Зачем проверять по коду выхода: так это можно засунуть в cron или в мониторинг.
</details>

## Часть 2. Поломки

```bash
docker rm -f tls      # кейсы на другом порту, но чтобы не путаться
./lab.sh 1            # поднять кейс 1, пишет симптом
./lab.sh check        # починил или нет
```

Файлы кейса лежат на хосте в `cases/caseN/`. В контейнере `tls-case` они видны как `/etc/nginx/conf.d/`.
`lab.sh` не открывай, там ответы.

Порядок для любого TLS-инцидента:
1. посмотреть, что **отдаёт сервер**, а не что лежит на диске
2. прочитать ошибку целиком: она почти всегда говорит, какая проверка не прошла
3. посмотреть файлы
4. после правки проверить конфиг, потом сделать reload

**Кейс 1.** Вчера серт продлили, файл свежий. Клиенты всё равно видят `certificate has expired`.

**Кейс 2.** В браузере сайт открывается, а curl и мобилки ругаются.

<details><summary>подсказка</summary>

Посчитай, сколько сертов отдаёт сервер, как ты делал с github.com. Сравни, сколько было там.
В `TLS.md` смотри раздел про файлы Let's Encrypt.
</details>

**Кейс 3.** После выкатки нового серта nginx не стартует.

<details><summary>подсказка</summary>

Ключей в папке несколько. Как узнать, какой из них от этого серта, не перебирая их по очереди?
Перебор наугад не засчитывается.
</details>

Убрать за собой:

docker rm -f tls tls-case
./lab.sh clean
