## 1. Зачем nginx перед приложением

```
клиент ──> nginx :80/:443 ──> приложение :8080   (upstream, он же бэкенд)
```

nginx стоит на входе, приложение прячется за ним. Что это даёт:
- одна точка входа: по пути или домену nginx решает, в какое приложение отправить запрос
- TLS в одном месте: серты лежат у nginx, приложение говорит обычным http
- раздача статики, таймауты, лимиты, балансировка на несколько копий
- приложение не торчит наружу: его порт открыт только для nginx

Такая схема называется **reverse proxy**. Сервер за nginx в его логах и доке зовётся **upstream**.
В k8s это Ingress: ingress-nginx — тот же nginx с таким же конфигом внутри. В 2026 его сняли с поддержки, и новые кластеры переходят на Gateway API. Но в старых кластерах он стоит повсюду, а 502/504 и таймауты там ровно такие же.

## 2. Как устроен конфиг

- в образе `nginx:alpine` главный файл `/etc/nginx/nginx.conf` подключает `/etc/nginx/conf.d/*.conf`. Поэтому в лабе монтируется именно `conf.d`
- директива заканчивается на `;`, блок пишется в `{ }`, комментарий начинается с `#`
- вложенность такая: `http` → `server` (один сайт) → `location` (один путь внутри сайта)

```nginx
server {
    listen 80;                     # какой порт слушать

    location / {
        return 200 "hi\n";         # ответить самому
    }
}
```

У location есть три способа ответить:
- `return` — nginx отвечает сам кодом и текстом (заглушки, редиректы, 403)
- `root` — отдать файл с диска
- `proxy_pass` — переслать запрос в приложение и вернуть клиенту его ответ

## 3. Какой location выберет nginx

- `location /api/ { }` — **префикс**: подходит любой путь, который начинается с этой строки
- `location = /version { }` — **точное** совпадение, только этот путь
- совпадение ищется **по строке, а не по «папкам»**. Что из этого следует для `location /api` без слэша, увидишь в задании 2

Как выбирает:
1. есть точное `=` → берёт его
2. иначе из всех подходящих префиксов берёт **самый длинный**. Порядок блоков в файле для префиксов роли не играет
3. (бывают ещё regex-location `~`, они проверяются по порядку. В лабе их нет)

**Один location ловит все пути под своим префиксом.** Перечислять пути приложения не надо:
```
location /api/ { ... }

/api/health        ─┐
/api/v1/orders     ─┼─>  начинаются с /api/  →  этот location  →  приложение
/api/v1/report     ─┤
/api/что-угодно    ─┘
/about             ───>  не начинается с /api/  →  сюда не попадает
```
nginx не знает, какие пути есть у приложения, и знать не должен. Он пересылает всё, что под префиксом, а приложение само решает, где 200, а где 404.

Отдельный location пишут, только если части путей нужно **другое поведение**: закрыть `/api/admin/` (задание 3), дать отчёту свой таймаут (кейс 2).
Такой location пишется **рядом** с `/api/`, а не внутри. Самый длинный префикс победит сам (правило выше).
Вложить location внутрь можно, но внутренний обязан начинаться с внешнего: внутри `/api/` можно `/api/admin/`, а `/health` нельзя (`location "/health" is outside location "/api/"`). В лабе вкладывать не нужно.

Не подошёл ни один location → nginx сам отвечает 404.

**Кто ответил 404: nginx или бэкенд?** Смотри на тело ответа:
- HTML-страница с `nginx/1.30.5` внизу — это nginx. Запрос до бэкенда даже не дошёл
- текст самого приложения (у api это `api: no route for ...`) — это бэкенд. nginx переслал запрос, просто путь оказался не тот

## 4. proxy_pass и путь

Как nginx находит бэкенд:
- в одной docker-сети контейнер виден по имени: `proxy_pass http://api:8080`
- имя nginx резолвит **один раз**, при старте и на reload. Если контейнера api нет, nginx не стартует:
  `[emerg] host not found in upstream "api"`. Поэтому сначала `./lab.sh up`, потом nginx

Какой путь получит бэкенд. Тут всё решает, есть ли что-то **после порта** в proxy_pass.

**После порта пусто** (`http://backend:5000`): nginx путь не трогает, отправляет как есть.

**После порта что-то есть**, хоть один `/`: nginx делает «найти и заменить» в начале пути. Убирает префикс location и на его место ставит то, что написано после порта.
Склеивает буквально, как строки, лишние или недостающие слэши не правит.

Считается в три шага:
```
запрос                 /shop/cart
1. убрать префикс      /shop/cart  минус  /shop/   →  cart
2. что после порта     http://backend:5000/v2/      →  /v2/
3. склеить             /v2/  +  cart                →  /v2/cart
```

Примеры. Проверено на живом nginx, в последней колонке то, что бэкенд записал в свой лог:

| location | proxy_pass | запрос | бэкенд получил |
|---|---|---|---|
| `/shop/` | `http://backend:5000/` | `/shop/cart` | `/cart` |
| `/shop/` | `http://backend:5000/` | `/shop/cart/42` | `/cart/42` |
| `/shop/` | `http://backend:5000/v2/` | `/shop/cart` | `/v2/cart` |
| `/shop/` | `http://backend:5000` | `/shop/cart` | `/shop/cart`: после порта пусто, путь как есть |
| `/shop/` | `http://backend:5000/v2` | `/shop/cart` | `/v2cart`: склеил буквально, `/v2` + `cart` |

Последняя строка — частая ошибка в проде: потеряли слэш в конце, и пути склеились.

Прогони по трём шагам все три варианта из задания 2 **до** того, как запускать curl.

Какой путь nginx реально отправил, видно в двух местах: в логе бэкенда и в поле `upstream:` строки error log (раздел 6).

В проде к proxy_pass почти всегда добавляют заголовки, иначе приложение не узнает, кто к нему пришёл:
```nginx
proxy_set_header Host $host;                                   # домен, который просил клиент
proxy_set_header X-Real-IP $remote_addr;                       # IP клиента, а не nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # цепочка прокси
```
Для лабы они не нужны.

## 5. Когда nginx читает конфиг. reload и restart

Внутри nginx есть **master** и **workers** (видно в `docker exec proxy ps`). Master читает конфиг, workers обслуживают запросы.

**Конфиг и серты** nginx читает только при старте и на reload. Поменял файл — до reload ничего не изменится (это была Geneva).
**Файлы из `root` и ответы бэкенда** он берёт на каждый запрос, тут reload не нужен.

| команда | что делает |
|---|---|
| `nginx -t` | проверяет конфиг. Ничего не применяет |
| `nginx -T` | проверяет и печатает весь конфиг **с диска**. Это не то, что сейчас работает |
| `nginx -s reload` | master перечитывает конфиг. Если он рабочий, поднимаются новые workers, а старые дообслуживают свои запросы и выходят: даунтайма нет. Если в конфиге ошибка — пишет её, и **продолжает работать старый конфиг** |
| restart (`docker restart`, `systemctl restart nginx`) | процесс умирает, все соединения рвутся. Если в конфиге ошибка, nginx не поднимется, и сайт лежит |

В докере: `docker exec <контейнер> nginx -t`. На обычном сервере: `systemctl reload nginx` (то же, что `-s reload`).

Порядок на проде: правка → `nginx -t` → reload → проверить curl'ом → глянуть error log.

Ошибка в конфиге выглядит так: `[emerg] unexpected "}" in /etc/nginx/conf.d/default.conf:12`.
Номер строки — это место, где nginx споткнулся. Сама ошибка часто сидит строкой выше, например забытая `;`.

В Ansible то же самое делают через handler:
```yaml
- name: nginx config
  template:
    src: site.conf.j2
    dest: /etc/nginx/conf.d/site.conf
  notify: reload nginx          # дёрнуть handler, только если файл реально поменялся

handlers:
  - name: reload nginx
    service:
      name: nginx
      state: reloaded           # reload, а не restarted
```
Handler выполняется один раз в конце play, и только если задача с notify вернула `changed`.

## 6. Логи

- **access log**: каждый запрос и код ответа
- **error log**: почему не получилось. Для прокси главное тут
- в образе nginx оба лога идут в stdout/stderr → `docker logs <контейнер>`. На обычном сервере они лежат в `/var/log/nginx/`

Строку error log разбирай по кускам:
```
[error] ... connect() failed (111: Connection refused) while connecting to upstream,
  client: 172.19.0.1, request: "GET /api/health HTTP/1.1", upstream: "http://172.19.0.3:8080/health"
```
- `connect() failed (111: Connection refused)` — что сломалось: системный вызов и код ошибки
- `while connecting to upstream` — **на каком шаге**: подключался, ждал ответ, читал ответ
- `request:` — что просил клиент
- `upstream:` — куда nginx пошёл на самом деле: IP, порт и путь, который он отправил

Коды ошибок, которые встретишь: `111` — refused (порт закрыт), `110` — timed out (ждал и не дождался), `113` — no route to host (такого хоста в сети нет).
Текст после номера зависит от системы: в alpine `Operation timed out`, в Ubuntu `Connection timed out`. Смотри на номер.

## 7. 502 и 504

Оба кода выдаёт **сам nginx**. Сам он жив, проблема за ним. А вот 500 обычно приходит от приложения: nginx просто передаёт его дальше.

**502 Bad Gateway**: нормального ответа от бэкенда не получилось.
- `connect() failed (111: Connection refused) while connecting` — на этом IP:порту никто не слушает: процесс умер, не тот порт или приложение слушает другой адрес (раздел 8). Отказ приходит **сразу**
- `upstream prematurely closed connection while reading response header` — бэкенд принял запрос и оборвал соединение, не ответив (упал посреди запроса)

**504 Gateway Timeout**: nginx ждал и сдался. Бывает двух видов, и отличаются они словами после `while`:
- `upstream timed out (110) while connecting to upstream` — даже подключиться не смог: пакеты молча выбрасываются (DROP в файрволе, как в Cairo). Лимит — `proxy_connect_timeout`
- `upstream timed out (110) while reading response header from upstream` — подключился, отправил запрос, а бэкенд слишком долго молчит. Бэкенд жив, но медленный или завис. Лимит — `proxy_read_timeout`

У обоих таймаутов умолчание **60 секунд**. `proxy_read_timeout` считается между двумя чтениями, а не на весь ответ.
Таймауты можно задать в `http`, `server` или `location`. Чем ниже уровень, тем точнее: значение в location перекрывает значение из server.

Refused и DROP — разные вещи. Порт закрыт → ядро сразу отвечает «нет» (RST) → быстрый 502. Пакеты выбрасываются → тишина → nginx ждёт до таймаута → 504.

Поднять таймаут — пластырь, а не лечение. Делают это точечно, на один медленный путь. Настоящий фикс — ускорить запрос или сделать его фоновым: «задача принята, статус смотри тут».

## 8. Какой адрес слушает приложение

- `127.0.0.1:8080` — только loopback. Достучаться можно лишь изнутри того же сетевого пространства (тот же хост или тот же контейнер)
- `0.0.0.0:8080` — все интерфейсы: можно прийти снаружи
- смотреть колонку Local Address в `ss -tln` или `netstat -tln`

В докере у каждого контейнера своя сеть и свой `127.0.0.1`. «Отвечает на 127.0.0.1 внутри контейнера» не значит «доступен из соседнего контейнера».
А на обычном сервере бэкенд за nginx на `127.0.0.1` — это как раз правильно: до него доходит только nginx с того же хоста.

Это ты уже трогал руками в лабе 04.10 (`python -m http.server --bind`).

Вся цепочка одного запроса на примере кейса 1:
```
НОУТБУК
  curl localhost:8082/api/health
     │
     │  1. порт 8082 ноутбука проброшен в nginx (-p 8082:80)
     ▼
┌─ case-proxy (nginx), адрес 172.19.0.4
│  2. /api/health подходит под location /api/
│     → отрезает /api/ → путь /health
│  3. «case-api — это кто?» докер отвечает: 172.19.0.3
└─────┬
      │  4. стучится на 172.19.0.3:8080
      ▼
┌─ case-api, listen=127.0.0.1
│  api ждёт на      127.0.0.1:8080   ← только для себя
│  nginx пришёл на  172.19.0.3:8080  ← тут никого → refused
└─────
      5. nginx получил refused → отдаёт тебе 502
```
С `listen=0.0.0.0` меняется только последний ящик:
```
┌─ case-api, listen=0.0.0.0
│  api ждёт на      127.0.0.1:8080
│  api ждёт и на    172.19.0.3:8080  ← nginx пришёл сюда → api ответил ok
└─────
      5. nginx получил ok → отдаёт тебе 200
```
