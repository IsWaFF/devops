# Nginx как прокси

Цель: поставить nginx перед приложением и починить три типичные поломки: 502, 504 и конфиг, который не применился.
Это nginx-карточки со страницы «Дыры с теста»: 502/504, слэш в proxy_pass, reload. Плюс `0.0.0.0`.
В k8s всё то же самое: ingress-nginx — это nginx, и внутри у него такой же конфиг.

Теория лежит в `NGINX.md`. Перед частью 1 прочитай разделы 1–4 (≈15 минут), перед частью 2 — разделы 5–8. Готового конфига там нет, но всё нужное для заданий есть.

Часть 1 ≈ 30 минут, часть 2 ≈ 40. На воскресенье хватит и одной части 1.
После каждого задания пиши «проверь N». Контейнеры, логи и файлы смотрю сам.

---

## Что есть

`./lab.sh up` поднимает учебный API в контейнере `api`. Он сидит в docker-сети `proxylab` и слушает порт 8080. Наружу порт не проброшен, так что снаружи до api можно добраться только через твой nginx.

Что умеет api:

| запрос | ответ |
|---|---|
| `GET /health` | `ok`, сразу |
| `GET /v1/orders` | список заказов, сразу |
| `GET /v1/report` | отчёт, считается 20 секунд |
| `GET /v1/stuck` | зависает (баг у разработчиков) |
| всё остальное | 404 `api: no route for <путь>` |

Каждый запрос api пишет в свой лог вместе с путём, который до него дошёл: `docker logs api`.

## Часть 1. Прокси своими руками

```bash
./lab.sh up
mkdir nginx
```

**1.** Напиши `nginx/default.conf`: nginx слушает порт 80 и всё, что начинается на `/api/`, отправляет в api. Подними его:

```bash
docker run -d --name proxy --network proxylab -p 8081:80 -v ./nginx:/etc/nginx/conf.d nginx:1.30-alpine
```

Теория: разделы 2 и 4.

Засчитано, когда `curl localhost:8081/api/v1/orders` отдаёт заказы.
Посмотри в `docker logs api`, какой путь дошёл до api.

<details><summary>подсказка</summary>

Контейнеры в одной docker-сети находят друг друга по имени, поэтому для nginx адрес api — `api:8080`.
Нужна одна директива из модуля `ngx_http_proxy_module`.
Если nginx не стартует, смотри `docker logs proxy`.
</details>

<details><summary>подсказка 2</summary>

Получаешь `api: no route for /api/v1/orders`? У api нет путей `/api/...`, у него есть `/v1/...`.
Префикс `/api` нужен только nginx'у, до api он доходить не должен. Дело в одном символе.
</details>

**2.** Попробуй по очереди три варианта. Для каждого запиши, какой путь увидел api на `curl localhost:8081/api/v1/orders`:

| location | proxy_pass |
|---|---|
| `/api/` | `http://api:8080` |
| `/api/` | `http://api:8080/` |
| `/api` | `http://api:8080/` |

Перед каждым curl сначала угадай ответ по формуле из раздела 4, потом проверь.
На третьем варианте сходи ещё и на `localhost:8081/apiv1/orders`. Такого адреса быть не должно. Что вышло?

Сформулируй правило своими словами: когда nginx отрезает префикс location, а когда отдаёт путь как есть.

<details><summary>подсказка</summary>

Поменял файл, а ответ тот же? Вспомни Geneva.
Контейнер не перезапускай и не пересоздавай.
</details>

**3.** Верни рабочий вариант и добавь второй location: `/api/admin/` отвечает 403 и в api не ходит.
Нужно так: `/api/admin/users` даёт 403, а `/api/v1/orders` по-прежнему отдаёт заказы.

Потом поменяй два блока местами. Что-то изменилось?
Почему nginx выбирает `/api/admin/`, хотя `/api/` тоже подходит? (раздел 3)

<details><summary>подсказка</summary>

Директива `return`.
</details>

## Часть 2. Поломки

```bash
docker rm -f proxy        # кейсы на другом порту, но чтобы не путаться
./lab.sh 1                # поднять кейс 1, пишет симптом
./lab.sh check            # починил или нет
```

Кейс поднимает свою пару контейнеров `case-proxy` и `case-api` на порту 8082.
Файлы лежат в `cases/caseN/nginx/` и `cases/caseN/api/`. `lab.sh` не открывай, там ответы.

Теория: разделы 5–8 в `NGINX.md`.

Порядок для любой ошибки прокси:
1. код ответа: `curl -i`
2. error log nginx: `docker logs case-proxy`. Строку читай целиком, до конца.
3. сам бэкенд: жив ли он, что пишет в лог, отвечает ли изнутри своего контейнера
4. только потом файлы

**Кейс 1.** После переезда api в новый контейнер весь `/api/` отдаёт 502.
`docker ps` говорит, что case-api работает, а разработчик клянётся: «изнутри контейнера всё отвечает».

Найди причину командами, файлы открывай потом. Теория: разделы 7 и 8.
Проверь слова разработчика сам. Почему «изнутри отвечает» ничего не доказывает?
После правки настроек api перезапусти его: `docker restart case-api`.

<details><summary>подсказка</summary>

В образе api нет ss и curl, зато есть `netstat` и `wget`:
`docker exec case-api netstat -tln`
`docker exec case-api wget -qO- 127.0.0.1:8080/health`
(Пиши именно 127.0.0.1, не localhost: у busybox localhost уходит в IPv6 `::1`.)
`127.0.0.11` в netstat — это DNS докера, его не трогай.
Сравни адрес, который слушает api, с лабой 04.10 про `http.server --bind`.
</details>

**Кейс 2.** Отчёт `/api/v1/report` падает с 504. `/api/health` отвечает сразу, api живой, ошибок в его логах нет.

Найди, через сколько секунд приходит 504 и откуда взялась эта цифра. Теория: раздел 7.
Почини так, чтобы долгий таймаут был только у отчёта. Остальным путям 10 секунд хватает, а зависший `/api/v1/stuck` пусть, как и раньше, обрывается быстро. `check` проверяет и это.

<details><summary>подсказка</summary>

`curl -o /dev/null -w '%{http_code} %{time_total}\n' ...` покажет код и сколько ждал.
В строке error log главное — слова после `while`. Сравни их со строкой из кейса 1.
Подожди ещё 10 секунд и загляни в `docker logs case-api`.
</details>

<details><summary>подсказка 2</summary>

Отдельный location для отчёта. Как написать в нём proxy_pass, ты разобрался в задании 2.
</details>

В тесте отчёт падал ровно через минуту, хотя таймаута в конфиге не было вообще. Откуда взялась минута?

**Кейс 3.** Коллега вчера добавил в конфиг `location = /version` для мониторинга. В файле он есть, а `curl localhost:8082/version` даёт 404.

Почини без даунтайма: `case-proxy` не перезапускать. `check` проверяет и это. Теория: раздел 5.

<details><summary>подсказка</summary>

Сначала ответь себе, когда nginx читает конфиг.
Потом вспомни, какой командой конфиг проверяют до того, как его применить.
</details>

<details><summary>подсказка 2</summary>

nginx показывает строку, на которой споткнулся. Сама ошибка часто сидит строкой выше.
</details>

**3+.** Когда засчитаю: верни опечатку коллеги и сделай reload. Сайт отвечает?
Теперь сделай `docker restart case-proxy`. Отвечает?
Объясни разницу. Потом почини опечатку и подними контейнер: `docker start case-proxy`.
