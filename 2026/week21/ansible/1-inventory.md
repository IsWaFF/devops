# Блок 1. Inventory, ad-hoc, модули

Цель: Ansible видит три сервера и выполняет на них команды, пока без единого плейбука.

Время: около 40 минут.

---

## Шаг 1. Как Ansible ходит на серверы

### Теория

- Ansible стоит только у тебя на ноуте (**control node**). На серверах (**managed nodes**) его нет: там нужны только sshd и python. Это и называется **agentless**
- что происходит на каждую задачу: Ansible заходит по SSH, кладёт на сервер маленькую python-программу (**модуль**), запускает её, забирает ответ и удаляет её
- команду запускаешь ты, и Ansible сам идёт на серверы: это **push**-модель. В pull-модели (Puppet, Chef) агент на сервере раз в N минут сам забирает конфигурацию
- список серверов называется **inventory**. Серверы в нём собраны в группы:

```ini
[db]
db1 ansible_host=10.0.0.5 ansible_port=22
db2 ansible_host=10.0.0.6

[db:vars]
ansible_user=admin
```

- `db1` — имя, под которым сервер знает Ansible. С настоящим hostname оно совпадать не обязано
- `ansible_host`, `ansible_port`, `ansible_user` — куда и кем заходить по SSH
- `[db:vars]` — переменные сразу для всей группы
- группа `all` есть всегда, в ней все серверы. `[all:vars]` тоже можно

Остальные настройки (где инвентарь, каким ключом входить) лежат в `ansible.cfg`. Он уже готов, открой и прочитай.

### Руками

**1.** Подними стенд и зайди на сервер обычным ssh:

```bash
./lab.sh up
./lab.sh ssh web1
```

На сервере посмотри `hostname`, `whoami`, `sudo whoami` и выйди. Вход по ключу и sudo: больше Ansible от сервера ничего не нужно.

**2.** Напиши `inventory.ini`: группа `web` с серверами web1 и web2, группа `lb` с сервером lb1. Адреса и порты показывает `./lab.sh status`. Пользователь `deploy` один на всех.

**3.** Проверь:

```bash
ansible-inventory --graph
ansible all -m ping
```

Должно прийти три `pong`. Этот `ping` не ICMP: модуль заходит по SSH и запускает python. Раз pong пришёл, Ansible может работать с сервером.

## Шаг 2. Ad-hoc команды и модули

### Теория

Ad-hoc — это один запуск одного модуля без плейбука:

```
ansible <на ком> -m <модуль> -a "<аргументы>" [-b]
```

- на ком: имя группы, имя сервера или `all`
- `-b` (become) — выполнить через sudo

Модулей сотни, в работе нужен десяток:

| модуль | что делает |
|---|---|
| `apt` | пакеты |
| `service` | сервисы: запущен, остановлен, в автозагрузке |
| `copy` | положить файл как есть |
| `template` | положить файл, подставив в него переменные |
| `file` | права, каталоги, симлинки, удаление |
| `user` | пользователи |
| `lineinfile` | одна строка в файле |
| `command`, `shell` | произвольная команда |

`command` запускает программу напрямую, без шелла: `|`, `>`, `&&`, `$HOME` в нём не работают. `shell` запускает через `/bin/sh`, и там это всё работает.

### Руками

**4.** Сравни:

```bash
ansible all -m command -a "whoami"
ansible all -b -m command -a "whoami"
```

**5.** Спроси у серверов, что они о себе знают. Это **факты**, подробно о них в блоке 3:

```bash
ansible lb -m setup -a "filter=ansible_distribution*"
```

**6.** Запусти и прочитай ошибку:

```bash
ansible web1 -m command -a "cat /etc/os-release | grep VERSION"
```

Почему `cat` жалуется на файл с именем `|`? Исправь команду, поменяв в ней одно слово.

## Шаг 3. Идемпотентность

### Теория

- модуль описывает **состояние**, а не действие. Не «установи htop», а «htop установлен». Если так уже и есть, модуль ничего не делает
- в ответе `CHANGED` значит «модуль что-то изменил», `SUCCESS` значит «уже было как надо» (в плейбуках это `changed` и `ok`)
- отсюда **идемпотентность**: сколько раз ни запусти, итог на сервере один и тот же, и второй запуск уже ничего не меняет
- `command` и `shell` о состоянии ничего не знают. Они каждый раз `CHANGED`, а на втором запуске могут и упасть

### Руками

**7.** Запусти два раза подряд и сравни ответы:

```bash
ansible web -b -m apt -a "name=htop state=present update_cache=true"
```

**8.** То же с каталогом, два раза:

```bash
ansible web -b -m file -a "path=/opt/lab state=directory mode=0755"
```

**9.** А теперь «то же самое» командой, два раза:

```bash
ansible web -m command -a "mkdir /tmp/x"
```

Сравни второй запуск здесь и в задании 8. Это и есть разница между модулем и командой.

## Грабли

| что видишь | что это |
|---|---|
| `UNREACHABLE!` и `ssh: connect to host 127.0.0.1 port 2209: Connection refused` | Ansible не смог зайти по SSH: не тот порт или адрес, сервер не запущен. До модуля дело не дошло |
| `UNREACHABLE!` и `Permission denied (publickey,password)` | зашёл не тем пользователем или не тем ключом |
| `FAILED!` | зайти получилось, модуль отработал и вернул ошибку. Причина в `msg` |
| `No package matching 'htop' is available` | на свежем сервере кеш apt пустой. Нужен `update_cache=true`, это тот же `apt update` перед `apt install` |
| `E: Could not open lock file /var/lib/dpkg/lock-frontend ... are you root?` | забыл `-b` |

`UNREACHABLE` и `FAILED` — разные вещи: первое чинится в инвентаре и сети, второе в задаче.
