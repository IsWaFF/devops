# Блок 2. Playbook и идемпотентность

Цель: nginx на двух серверах ставится и настраивается из файла, который лежит в git. Второй запуск файла ничего не меняет.

Время: около 50 минут.

---

## Шаг 1. Первый плейбук

### Теория

Ad-hoc команды нигде не остаются. Плейбук — это YAML-файл с тем же самым, его можно прочитать, закоммитить и запустить ещё раз.

```yaml
- name: Database servers          # play: на каких серверах и что делать
  hosts: db
  become: true                    # все задачи этого play через sudo
  tasks:
    - name: Install postgres      # task: один вызов одного модуля
      ansible.builtin.apt:        # модуль
        name: postgresql          # аргументы модуля
        state: present
```

- цепочка такая: **playbook** (файл) → **play** (группа серверов и список задач) → **task** → **модуль**
- в одном файле может быть несколько play, для разных групп
- `ansible.builtin.apt` — полное имя модуля. Короткое `apt` тоже работает, но в плейбуках принято писать полное
- задачи идут сверху вниз. Каждая выполняется на всех серверах play, потом следующая
- отступы только пробелами, по два

Запуск и итог:

```
ansible-playbook web.yml

PLAY RECAP
web1 : ok=3  changed=1  unreachable=0  failed=0 ...
```

- `ok` — сколько задач отработало без ошибки (вместе с changed)
- `changed` — сколько из них что-то изменили на сервере
- `failed` — упало. Сервер, на котором задача упала, дальше по плейбуку не идёт
- задачу `Gathering Facts` Ansible добавляет сам: собирает сведения о сервере (блок 3)

Флаги, которые нужны каждый день:

| флаг | зачем |
|---|---|
| `--syntax-check` | проверить YAML и структуру, ничего не запуская |
| `--list-tasks` | показать, какие задачи есть в плейбуке |
| `--check` | ничего не менять, только показать, что изменилось бы |
| `--diff` | показать разницу в файлах, которые меняются |
| `--limit web1` | выполнить только на части серверов |

### Руками

**1.** Напиши `web.yml`: один play для группы `web` с двумя задачами.
- nginx установлен. Модуль `apt`, и не забудь про кеш: `update_cache: true` и `cache_valid_time: 3600` (обновлять кеш не чаще раза в час, иначе каждый прогон начинается с `apt update`)
- nginx запущен и стоит в автозагрузке. Модуль `service`, параметры посмотри в `ansible-doc -s service`

**2.** Запусти. Потом `curl localhost:8101` и `curl localhost:8102`: оба отдают «Welcome to nginx!».

**3.** Запусти второй раз. В RECAP должно быть `changed=0`.

## Шаг 2. Файлы: copy и file

### Теория

- `copy` кладёт файл с ноута на сервер: `src` (путь относительно плейбука, по соглашению папка `files/`), `dest`, плюс `owner`, `group`, `mode`
- файл меняется, только если отличается содержимое или права. Положил тот же файл второй раз → `ok`
- `file` не про содержимое, а про всё остальное: `state: directory`, `link`, `absent` (удалить), `touch`, и права
- `mode` пиши в кавычках и с нулём в начале: `"0644"`. Голое `644` YAML прочитает как обычное число, и права получатся не те
- `--check --diff` перед настоящим запуском отвечает на вопрос «что сейчас изменится»

### Руками

**4.** Сделай `files/index.html` с любой своей строкой и добавь в плейбук задачу, которая кладёт его в `/var/www/html/index.html`. Запусти, curl показывает твою страницу.

**5.** Поменяй текст в `files/index.html`. Сначала запусти так:

```bash
ansible-playbook web.yml --check --diff
```

Прочитай diff. Проверь curl-ом, что на серверах ещё старый текст. Потом запусти без `--check`.

**6.** Поменяй текст ещё раз и накати только на web1 (`--limit`). Сравни два порта curl-ом. Потом накати на всех.

## Шаг 3. Когда плейбук не идемпотентный

### Теория

Признаки, что второй прогон будет не `changed=0`:

- **`command` или `shell` там, где есть модуль.** Команда каждый раз `changed`, а то и падает на втором прогоне. Модуль есть почти на всё: `user`, `file`, `lineinfile`, `apt`, `service`, `git`, `cron`, `unarchive`. Найти: `ansible-doc -l | grep -i user`
- если модуля правда нет, команде объясняют, когда её не надо запускать:

```yaml
- name: Init the database
  ansible.builtin.command: /opt/app/init-db.sh
  args:
    creates: /opt/app/.db-ready     # этот файл уже есть → задача пропускается

- name: Check nginx config
  ansible.builtin.command: nginx -t
  changed_when: false               # команда только читает, changed не считать
```

- **`state: touch`** у `file` на каждом прогоне обновляет время файла → каждый раз `changed`
- **`state: restarted`** у `service` перезапускает сервис на каждом прогоне. Для «сервис должен работать» есть `started`. Перезапуск по делу будет в блоке 4
- **`state: latest`** у `apt`. Тут `changed=0`, но беда другая: сегодня это одна версия, через месяц другая. Плейбук тот же, а серверы получаются разные. Обычно пишут `present`, а обновляют отдельно и осознанно. По той же причине `upgrade: dist` в обычном плейбуке не держат

### Почини

`fixme/2-march.yml` готовит сервер под приложение. Запусти его два раза:

```bash
ansible-playbook fixme/2-march.yml
ansible-playbook fixme/2-march.yml
```

Первый раз проходит, второй падает. Сделай так, чтобы второй прогон давал `changed=0` и `failed=0`, а на серверах после него было:

- системный пользователь `app` без домашнего каталога
- каталог `/opt/app/releases`
- файл `/opt/app/.prepared`
- в `/opt/app/deploy.log` строка `deployed by ansible`, и повторные прогоны новых строк не добавляют
- curl установлен, nginx работает

Условие: `command` и `shell` в файле остаться не должно. Модули подбери сам через `ansible-doc`.

<details>
<summary>Подсказка про .prepared</summary>

У модуля `file` есть параметры про время файла. Смотри `ansible-doc file`, ищи `modification_time`.
</details>

<details>
<summary>Подсказка про deploy.log</summary>

Модуль `lineinfile`. Файла может ещё не быть: у модуля есть параметр на этот случай.
</details>

## Грабли

| что видишь | что это |
|---|---|
| `YAML parsing failed: Tabs are usually invalid in YAML` | в отступе таб вместо пробелов |
| `conflicting action statements: ansible.builtin.apt, state` | аргументы модуля стоят на одном уровне с модулем. Их надо сдвинуть на два пробела вправо, под модуль |
| `No package matching 'nginx' is available` | у задачи с apt нет `update_cache: true` |
| `changed=1` на каждом прогоне | выше в выводе найди задачу со строкой `changed:` — это она не идемпотентна |
