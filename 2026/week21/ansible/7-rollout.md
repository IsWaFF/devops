# Блок 7. Балансировщик и раскатка по одному

Цель: перед двумя веб-серверами стоит балансировщик, новая версия выкатывается по одному серверу, и плохой релиз останавливается на первом.

Время: около часа. В конце вся инфраструктура собирается с нуля одной командой.

---

## Шаг 1. Балансировщик из инвентаря

### Теория

В шаблоне доступны не только переменные своего сервера:

- `groups['web']` — список серверов группы `web`
- `hostvars['web1']` — переменные и факты другого сервера

Отсюда обычный приём: конфиг балансировщика собирается из инвентаря. Добавил сервер в группу `web`, прогнал плейбук, и он уже в балансировке. Руками список никто не правит.

### Руками

**1.** Сделай роль `lb`. В шаблоне `lb.conf.j2` nginx-часть готовая, цикл допиши сам:

```nginx
upstream web {
    zone web 64k;
    # здесь цикл: строка "server <имя сервера>:80;" на каждый сервер группы web
}

server {
    listen 80 default_server;

    location / {
        proxy_pass http://web;
    }
}
```

`zone` даёт воркерам nginx общий счётчик запросов. Без неё серверы тоже чередуются, но у каждого воркера по-своему, и на глаз этого не видно.

Задачи в роли те же, что в роли `nginx`: пакет, шаблон в `sites-available`, симлинк в `sites-enabled`, убрать `default`, проверка `nginx -t`, сервис запущен, handler с reload.

**2.** Добавь в `site.yml` третий play: группа `lb`, роль `lb`. Запусти.

**3.** Спроси балансировщик несколько раз подряд:

```bash
curl -sI localhost:8100 | grep X-Served-By
```

Отвечают web1 и web2 по очереди.

## Шаг 2. serial и проверка после выката

### Теория

По умолчанию Ansible выполняет задачу сразу на всех серверах play, потом берёт следующую задачу. Плохой релиз при этом ломает все серверы одновременно.

`serial: 1` меняет порядок: весь play сначала целиком проходит на одном сервере, потом на следующем. Бывает `serial: 2` и `serial: "25%"`.

```yaml
- name: Web servers
  hosts: web
  become: true
  serial: 1
  roles:
    - nginx
  post_tasks:
    - name: Site answers 200
      ansible.builtin.uri:
        url: http://localhost/
        status_code: 200
```

- если на сервере задача упала, play на нём останавливается. При `serial`, если упала вся текущая пачка, Ansible дальше не идёт, и остальные серверы остаются на старой версии
- чтобы Ansible понял, что релиз плохой, после выката нужна проверка. Модуль `uri` делает HTTP-запрос с самого сервера и падает, если код не тот
- `post_tasks` выполняются после ролей. Handlers к этому моменту уже отработали, то есть reload прошёл и проверяется новый конфиг
- версию приложения держат переменной в git. Поменял `app_version`, закоммитил, прогнал плейбук: история git и есть история релизов

### Руками

**4.** Добавь `app_version: 1` в `group_vars/web/vars.yml` и выведи его на страницу строкой вида `version: 1`. В play для `web` добавь `serial: 1` и `post_tasks` с проверкой. Запусти.

**5.** Открой второй терминал и оставь в нём:

```bash
./lab.sh watch
```

Он раз в полсекунды спрашивает сайт через балансировщик и печатает код ответа, кто ответил и какая версия.

**6.** Поставь `app_version: 2` и запусти `site.yml`. В выводе Ansible видно, что сначала весь play прошёл на web1, потом на web2. В окне с watch версии 1 и 2 идут вперемешку, потом остаётся только 2. Ошибок нет.

## Шаг 3. Плохой релиз

### Теория

Сымитируем релиз, после которого приложение отвечает 500. В `roles/nginx/templates/lab.conf.j2` внутрь `server` добавь:

```jinja
{% if break_release | default(false) %}
    return 500;
{% endif %}
```

`| default(false)` — это фильтр: если переменная не задана, взять `false`. Обычный прогон без этой переменной ничего не меняет.

### Руками

**7.** Добавь этот кусок в шаблон и запусти `site.yml`: `changed=0`.

**8.** Закомментируй `serial: 1` и выкати плохой релиз:

```bash
ansible-playbook site.yml -e break_release=true
```

В окне с watch одни 500. Это простой: сломаны все серверы сразу. Откати тем же запуском без `-e`.

**9.** Верни `serial: 1` и выкати плохой релиз ещё раз. Посмотри на RECAP: у web1 `failed=1`, а web2 остановился на `ok=2`. Это задачи первого play, до веб-задач очередь не дошла. В окне с watch 200 и 500 через раз: ошибку видит половина пользователей, а не все.

**10.** Откати: запуск без `-e`.

**11.** По желанию: сделай из половины ноль. Пусть балансировщик, получив 500 от одного сервера, сам спросит другой. В `lb.conf.j2` в `location` добавь:

```nginx
proxy_next_upstream error timeout http_500;
```

Повтори задание 9: web1 сломан, а в окне с watch одни 200.

## Финал: всё с нуля

**12.** Запусти:

```bash
./lab.sh check final
```

Проверка сносит все три сервера, поднимает чистые и прогоняет `site.yml` два раза. Первый прогон должен пройти без ошибок, второй дать `changed=0`, сайт должен отвечать через балансировщик.

Ради этого Ansible и нужен: серверы можно выбросить и одной командой собрать точно такие же.

## Грабли

| что видишь | что это |
|---|---|
| `Status code was 500 and not [200]: HTTP Error 500: Internal Server Error` | сработала проверка после выката. Так и должно быть в заданиях 8 и 9 |
| `host not found in upstream "web3:80"` в `nginx -t` на lb1 | в upstream попало имя, которого нет в сети стенда. Проверь, что цикл идёт по `groups['web']` |
| в watch код 502 | балансировщик жив, а веб-серверы за ним не отвечают: nginx на них не запущен или ещё не установлен |
| в watch `000` или `---` | не отвечает сам балансировщик |
| балансировщик отвечает страницей «Welcome to nginx!» | на lb1 не убран `sites-enabled/default` |
